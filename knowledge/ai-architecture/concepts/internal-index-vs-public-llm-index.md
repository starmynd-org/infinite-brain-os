# Internal Index Versus Public LLM Index

## Summary

A namespace has two index-shaped artifacts that look similar and are not. The internal
`INDEX.md` is a rich retrieval router built for trusted agents that read the whole graph.
A public `llms.txt` is a thin discovery surface generated from `canon/` for external
consumers. They are different artifacts, with different readers, contents, write paths,
and trust boundaries (contract Part 10).

## Content

The two surfaces answer different questions for different readers.

`INDEX.md` answers "how do I retrieve correctly inside this namespace." It is the agent
operating brief: declared profile, load-first order, query classes mapped to files,
stable-versus-stateful split, open disputes, output linkage, common misreadings, and a
folder map. It is rich markdown without node frontmatter, and `validate.sh` exempts it
from node-frontmatter checks so it can stay dense. It assumes a trusted reader with full
graph access. Today that reader is a Claude Code or Codex agent reading files by grep and
read, per the retrieval-over-raw-memory posture.

`llms.txt` answers "what does this namespace publicly claim, summarized." It is a thin
public summary generated from `canon/`, never from raw notes, support material, or
synthesis. It is an export and discovery surface, not internal architecture. A generator
reads canon and emits the public file; it never bypasses canon and never publishes
internal-only material.

The differences, side by side:

- Reader: `INDEX.md` serves trusted internal agents; `llms.txt` serves external LLMs and
  crawlers.
- Source: `INDEX.md` is hand-curated over the whole namespace; `llms.txt` is generated
  from canon only.
- Depth: `INDEX.md` is a full router with query classes and failure modes; `llms.txt` is
  a compressed summary with links.
- Trust: `INDEX.md` may reference internal-only and department-scoped material;
  `llms.txt` may only carry material approved for public export.
- Write path: an agent edits `INDEX.md` directly during namespace work; `llms.txt` is
  regenerated by a tool from canon, not hand-edited.

## Which profiles expose a public index

A namespace exposes a public index only when it is meant for external discovery. The
decision is per namespace and recorded in the registry, not assumed by default.

- Most relevant: Tool Contract, Data System, Design System, Component Library, and
  Content Strategy. These describe capabilities, contracts, or positions that external
  readers and integrators reasonably want.
- Least relevant: private thinker canon such as `ooda-john-boyd` and `david-deutsch`, and the
  operator starter namespace. These stay internal; no public index is generated.

The operative gate lives in [[public-llm-index-export-posture]] and the
`_system/public-llm-index-policy.md` rules. The export decision is explicit per
namespace; a namespace without an approved export posture gets no `llms.txt`.

## What stays internal

Everything not promoted into canon stays internal and never reaches the public surface.
That includes `support/` provenance, `synthesis/` derived thinking, open questions,
intake receipts, and any node whose `export_class` is `internal` or `department`. The
public index draws only from operator-approved canon, which by contract is small,
provenance-bearing, and free of unresolved questions.

## Why the separation matters

Collapsing the two surfaces causes one of two failures. If the public file becomes the
router, agents lose the query-class depth they need and external readers see internal
churn. If the internal router is published, internal-only and half-formed material leaks.
Keeping them separate lets the internal index stay rich and current while the public
export stays thin, stable, and safe.

## Notes

`INDEX.md` is internal architecture; `llms.txt` is an export layer. When a namespace has
no approved export posture, it has an `INDEX.md` and no `llms.txt`, and that is the
expected state for most private namespaces.
